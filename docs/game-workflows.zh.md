# 完整游戏工作流

[English](game-workflows.md)

`plan_game_workflow` 与 `run_game_workflow` 面向无法靠一次小工具集可靠完成的完整目标。它们不会替代 217 个原子能力，而是把这些能力编译为持久计划，并依据客观证据推进到完成。

## 为什么完整工作流可以超过 8 个工具

既有路由器的默认 8 个、硬上限 10 个，是单次临时任务的发现与上下文预算，不是项目功能上限。

完整目标会保存为可包含大量原子步骤的 DAG。`run_game_workflow` 每轮最多推进 4 次原子调用，并且只在当前步骤缺参时返回所需字段和该工具的输入 Schema。隐藏的高级工具通过内部授权路径执行，不改变显隐状态，不重建 `tools/list`，也不清空发现缓存。

| 边界 | 上限 | 目的 |
| --- | ---: | --- |
| 临时路由工具集 | 默认 8，硬上限 10 | 控制单轮上下文 |
| 每轮原子调用 | 最多 4 | 控制编辑器负载、延迟和故障范围 |
| 完整持久 DAG | 随目标变化 | 不遗漏正确完成目标所需的能力 |
| 自动修复 | 默认 2 次，最多 3 次 | 防止无界修复循环 |
| 单步骤异步轮询 | 最多 120 次 | 防止永久 pending |
| 紧凑证据收据 | 最多 256 条 | 限制持久状态体积 |

不同 profile 的同名写操作不会被误删。例如玩家场景和暂停菜单场景会保留为两个带 `profile`、`step_key` 的独立 `create_scene` 步骤；相同确定性读取即使保留为独立语义步骤，也可由普通结果缓存避免重复扫描。

## 12 类可组合制作能力

| Profile | 完整闭环 |
| --- | --- |
| `gameplay_feature` | 检查项目/输入 → 创建场景、脚本与输入 → 保存 → 编译 → 游玩 → 运行时错误门禁 |
| `ui_screen` | 检查场景 → 创建主题/UI/布局 → 保存 → 运行时截图 → 视觉基线 |
| `script_repair` | 发现坏脚本 → 读取/修改 → 编译 → 项目测试 |
| `asset_pipeline` | 检查资源/导入 → 重导入 → 依赖与可选 glTF 校验 |
| `animation_audio` | 制作动画/关键帧 → 检查运行时动画和音频 → 应用状态 → 运行时证据 |
| `level_design` | 检查场景 → 创建场景/TileSet/单元格 → 保存 → 持久化和视觉门禁 |
| `runtime_debug` | 检查编辑器错误 → 启动探针/游戏 → 检查实时状态、输出与场景树 → 无错误门禁 |
| `localization` | 列出 → 提取 → 导入翻译 |
| `performance` | 采集运行时快照/内存趋势 → 可选优化代码 → 编译 → 性能预算和错误门禁 |
| `quality_assurance` | 发现测试 → 编译全部项目脚本 → 运行并轮询测试批次 |
| `project_health` | 审计脚本、依赖、循环和迁移；只有目标明确要求修复时才授权迁移写入 |
| `release_export` | 检查预设/模板 → 平台准备 → 校验 → 导出 → 产物冒烟测试 |

运行时步骤会自动补上 `install_runtime_probe` 与 `run_project` 前置条件。只有 Android 目标生成 Android 配置步骤；只读审计不会授权迁移写入。

## 基本用法

先规划完整目标：

```json
{
  "action": "plan",
  "objective": "创建可玩的 2D 控制器和暂停菜单，运行项目测试，并导出经过冒烟验证的 Linux 构建"
}
```

规划器只会返回三类结果：`planned`、需要澄清，或明确列出缺失能力。无法识别的目标不会被静默替换成通用玩法流程。

推进计划：

```json
{
  "expected_workflow_id": "<规划器返回的 id>",
  "max_steps": 4
}
```

当当前原子步骤需要参数时，执行器返回 `needs_input`、`step_id`、`tool_name`、`missing_inputs` 和按需 `input_schema`。只把参数交给该步骤：

```json
{
  "expected_workflow_id": "<同一个 id>",
  "step_inputs": {
    "wf_004": {
      "scene_path": "res://scenes/player.tscn",
      "root_node_type": "CharacterBody2D"
    }
  }
}
```

输入是临时数据：源码、路径或凭据不会写入持久目标合同。计划器拥有的控制参数（例如本地化 action）不能被 `step_inputs` 覆盖。

## 状态与完成条件

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `planned` / `running` | 仍有已授权步骤 | 再次调用执行器 |
| `needs_input` | 当前步骤缺少 Schema 必填字段 | 按返回的步骤 ID 提供参数 |
| `waiting` | 异步工具仍为 pending/running | 使用相同输入再次调用；不消耗修复次数 |
| `repairing` | 失败门禁存在已声明的有界修复 | 如有需要提供修复参数，然后重新验证 |
| `blocked` | 证据失败、能力消失、命中保护路径或修复用尽 | 修正原因后检查并重规划 |
| `recovery_required` | 分发后进程中断，写操作结果未知 | 检查项目再重规划；不会盲目重复写入 |
| `cancelled` | 客户端明确取消 | 新建或重规划 |
| `completed` | 所有步骤完成，所有目标门禁都有通过收据 | 目标合同满足 |

以下结果绝不会被当成完成：

- `pending`、`running`、`partial`、`skipped`、`unconfigured`、`stale`、超时或取消；
- 空验证结果；
- 未发现任何测试却报告测试通过；
- 存在失败脚本的编译验证；
- 没有测量 checks 的性能结论；
- 没有差异数据的视觉结论；
- 失败的项目健康审计；
- 手工把任务字段改为 `done`，但没有匹配的通过收据。

## 完整性与安全

每轮执行前，引擎都会从持久目标合同重新编译蓝图，并比较步骤顺序、工具、参数、依赖、profile、修复声明、目标门禁与 SHA-256 身份。蓝图发生变化时，在任何原子 handler 运行前停止。

默认保护 `res://addons/godot_mcp` 与 `res://.mcp`。候选路径会先解析和规范化，所以 `res://scenes/../addons/godot_mcp/...` 无法绕过保护。工作流内部禁止调用 Meta/控制工具，执行器也没有任意 `tool_name` 参数。

运行、重规划与取消都可使用 `expected_workflow_id` 做 CAS 校验，防止旧响应推进新计划。

## “完成”能保证什么

工作流保证：已注册能力计划不会被静默缩减，且没有声明的本地客观证据就不会报告成功。它不能凭空制造缺失资产、API 凭据、导出模板、平台 SDK、产品决策或项目尚未实现的原子能力。这些条件会以 `needs_input` 或 `blocked` 明确返回。只有这种失败关闭行为，才能让 `completed` 保持可信并在补齐前置条件后继续。
