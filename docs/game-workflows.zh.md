# 完整游戏工作流

[English](game-workflows.md)

`plan_game_workflow` 与 `run_game_workflow` 面向无法靠一次小工具集可靠完成的完整目标。它们不会替代 226 个原子能力，而是把这些能力编译为持久计划，并依据客观证据推进到完成。

## 为什么完整工作流可以超过 8 个工具

既有路由器的默认 8 个、硬上限 10 个，只是单次临时任务的可见发现与上下文预算，不是项目功能上限。完整目标的兜底路由可按语义子目标分别检索，再把名称合并进同一个持久计划，所以总工作流不受 10 个限制。

完整目标会保存为可包含大量原子步骤的 DAG。省略 `max_steps` 或设为 0 时，`run_game_workflow` 会依据剩余任务和历史轮次，自适应选择 4/8/16/32 次调用的检查点切片；正数只控制本次调用。到达切片边界只返回可续作让步，所有待办仍保留在持久 DAG 中。只有当前步骤缺参时才返回必要字段和该工具的输入 Schema。隐藏高级工具通过内部授权路径执行，不改变显隐状态，不重建 `tools/list`，也不清空发现缓存。

| 边界 | 上限 | 目的 |
| --- | ---: | --- |
| 临时路由工具集 | 默认 8，硬上限 10 | 控制单轮上下文 |
| 每轮原子调用 | 默认自适应 4/8/16/32；显式值仅影响本次调用 | 控制单轮负载但不限制完整目标 |
| 完整持久 DAG | 随目标变化 | 不遗漏正确完成目标所需的能力 |
| 自动修复 | 默认按证据自适应；可选正数调用方策略 | 证据变化时继续；相同失败连续 3 次后重规划 |
| 单步骤异步轮询 | 不设完成功能上限；每 120 次给出检查点标记 | 慢任务仍能完成，同时避免热循环 |
| 紧凑证据收据 | 不丢不同证据；相同轮询/结果聚合计数 | 保留证明且不重复膨胀 Token |

不同 profile 的同名写操作不会被误删。例如玩家场景和暂停菜单场景会保留为两个带 `profile`、`step_key` 的独立 `create_scene` 步骤；相同确定性读取即使保留为独立语义步骤，也可由普通结果缓存避免重复扫描。

## 12 类可组合制作能力

| Profile | 完整闭环 |
| --- | --- |
| `gameplay_feature` | 检查项目/输入 → 创建场景、脚本与输入 → 保存 → 编译 → 游玩 → 运行时错误门禁 |
| `ui_screen` | 检查场景 → 创建主题/UI/布局 → 保存 → 运行时截图 → 视觉基线 |
| `script_repair` | 发现坏脚本 → 读取/修改 → 编译 → 项目测试 |
| `asset_pipeline` | 检查资源/导入 → 重导入 → 依赖与可选 glTF 校验 |
| `animation_audio` | 制作动画/关键帧 → 检查运行时动画和音频 → 应用状态 → 运行时证据 |
| `level_design` | 检查场景 → 创建场景/TileSet/单元格 → 保存 → 持久化和视觉门禁 |
| `runtime_debug` | 检查编辑器错误 → 启动探针/游戏 → 检查实时状态、输出与场景树 → 无错误门禁 |
| `localization` | 列出 → 提取 → 导入翻译 |
| `performance` | 采集运行时快照/内存趋势 → 可选优化代码 → 编译 → 性能预算和错误门禁 |
| `quality_assurance` | 发现测试 → 编译全部项目脚本 → 运行并轮询测试批次 |
| `project_health` | 审计脚本、依赖、循环和迁移；只有目标明确要求修复时才授权迁移写入 |
| `release_export` | 检查预设/模板 → 平台准备 → 校验 → 导出 → 产物冒烟测试 |

运行时步骤会自动补上 `install_runtime_probe` 与 `run_project` 前置条件。只有 Android 目标生成 Android 配置步骤；只读审计不会授权迁移写入。

## 基本用法

最短路径是一条可重复发送的命令：

```json
{
  "command": "创建可玩的 2D 控制器和暂停菜单，运行项目测试，并导出经过冒烟验证的 Linux 构建"
}
```

如果检查点不存在，`run_game_workflow` 会先编译并保存目标，再执行第一个自适应切片。发生让步、暂时性故障、客户端断线或编辑器重启后，继续发送同一条命令即可；仅大小写和空白不同的命令会接回同一个工作流，已完成步骤不会再次分发。不同命令会返回 `conflict`，且不修改原检查点。

需要显式的两阶段控制时，可先规划完整目标：

```json
{
  "action": "plan",
  "objective": "创建可玩的 2D 控制器和暂停菜单，运行项目测试，并导出经过冒烟验证的 Linux 构建"
}
```

规划器只会返回三类结果：`planned`、需要澄清，或明确列出缺失能力。显式原子工具名一定成为目标证据；陌生复合目标可按语义子目标合并超过 10 个能力。如果仍有语义无法覆盖，会返回 `needs_clarification` 与 `uncovered_requirements`，绝不会把已匹配的局部计划冒充完整目标。

再推进计划：

```json
{
  "expected_workflow_id": "<规划器返回的 id>"
}
```

建议省略 `max_steps`（或传 `0`）启用自适应执行。正数可用于临时调小或调大本次负载，但不会删除或完成剩余任务。

当当前原子步骤需要参数时，执行器返回 `needs_input`、`step_id`、`tool_name`、`missing_inputs` 和按需 `input_schema`。只把参数交给该步骤：

```json
{
  "expected_workflow_id": "<同一个 id>",
  "step_inputs": {
    "wf_004": {
      "scene_path": "res://scenes/player.tscn",
      "root_node_type": "CharacterBody2D"
    }
  }
}
```

输入是临时数据：源码、路径或凭据不会写入持久目标合同。计划器拥有的控制参数（例如本地化 action）不能被 `step_inputs` 覆盖。

## 状态与完成条件

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `planned` / `running` | 仍有已授权步骤 | 再次调用执行器 |
| `needs_input` | 当前步骤缺少 Schema 必填字段 | 按返回的步骤 ID 提供参数 |
| `waiting` | 异步任务未结束，或暂时性故障已保留检查点 | 如有 `retry_after_ms` 先退避，再以相同输入续作；不消耗修复次数 |
| `repairing` / `retry_required` | 已声明修复可执行，或需更换输入/再次尝试 | 如有需要提供修复参数；证据变化时可继续 |
| `replan_required` | 同一失败连续 3 次、验证器无修复，或显式修复策略用尽 | 改变输入或能力组合，不重复相同无效工作 |
| `blocked` | 能力消失、完整性失败或命中保护路径 | 修正硬约束后重规划 |
| `recovery_required` | 非幂等写操作分发后发生重启，结果未知 | 检查项目再重规划；安全读取/幂等调用会自动重放 |
| `cancelled` | 客户端明确取消 | 新建或重规划 |
| `completed` | 所有步骤完成，所有目标门禁都有通过收据 | 目标合同满足 |

以下结果绝不会被当成完成：

- `pending`、`running`、`partial`、`skipped`、`unconfigured`、`stale`、超时或取消；
- 空验证结果；
- 未发现任何测试却报告测试通过；
- 存在失败脚本的编译验证；
- 没有测量 checks 的性能结论；
- 没有差异数据的视觉结论；
- 失败的项目健康审计；
- 手工把任务字段改为 `done`，但没有匹配的通过收据。

## 完整性与安全

每轮执行前，引擎都会从持久目标合同重新编译蓝图，并比较步骤顺序、工具、参数、依赖、profile、修复声明、目标门禁与 SHA-256 身份。蓝图发生变化时，在任何原子 handler 运行前停止。

每次保存都会先完整写入并验证 `.next`，再把已提交主文件轮换为 `.bak`，最后原子提升新检查点。恢复时会检查三代文件并选择 revision 最新的有效 JSON；即使写入被截断，或在两次重命名之间中断，最近可信状态也不会丢失。

新工作流使用版本化收据完整性：加载后会重新计算每条收据的摘要；每个 `done` 任务都必须引用属于自己的、最终通过且非修复用的收据。修改证据、伪造摘要或只切换任务状态，都会在执行前失败关闭。

默认保护 `res://addons/godot_mcp` 与 `res://.mcp`。候选路径会先解析和规范化，所以 `res://scenes/../addons/godot_mcp/...` 无法绕过保护。工作流内部禁止调用 Meta/控制工具，执行器也没有任意 `tool_name` 参数。

运行、重规划与取消都可使用 `expected_workflow_id` 做 CAS 校验；单命令入口还会比较归一化命令与持久目标，防止旧响应或另一条请求推进现有计划。

默认响应只是紧凑投影：最多返回 4 个就绪步骤的 ID、名称与阶段，以及进度和计数；除非设置 `include_plan=true` 或当前步骤确实缺参，否则不重复传输完整 DAG、参数、收据或原子 Schema。相同 pending 收据只增加出现次数，不同完成证据则一条不丢。

## “完成”能保证什么

工作流保证：已注册能力计划不会被静默缩减，且没有声明的本地客观证据就不会报告成功。它不能凭空制造缺失资产、API 凭据、导出模板、平台 SDK、产品决策或项目尚未实现的原子能力。这些条件会以 `needs_input` 或 `blocked` 明确返回。只有这种失败关闭行为，才能让 `completed` 保持可信并在补齐前置条件后继续。
